Agent — transcript redesign, and the new space flow

The Agent screen shipped with a transcript that gives every event the same weight: each tool call is a bordered, shadowed card the size of a message, so a single question that reads four things fills the screen with paperwork before the answer arrives. That is exactly backwards for this audience. The user's words and the agent's answer are the content; the machinery is a footnote.

Three changes here. One: the transcript becomes a quiet timeline — tool calls collapse to a single 44px line in the reply's gutter, and only a change that needs a press is a card. Two: the composer is untouched — same undo, delete-last-word, clear, audio-free Ask button, same 20px field. Three: /spaces/new stops being a bespoke three-step wizard and becomes the Agent's first conversation, so the tool-line component draws the space being made and the user can keep talking to it afterwards.

The one rule this redesign rests on. Anything the user must act on is a card. Everything else is a line. There is no third weight. Today the screen has one weight for everything, which is why a read looks as urgent as a delete.

5 · The new space flow becomes the Agent's first conversation

NewSpaceScreen is 300 lines inside pages/spaces.tsx that already does what the Agent does: take the user's words, call models, write to storage, and report each write as it lands. It has its own vocabulary for that — CreateProgress, createSteps(), StepState, a MARKS icon table and a Steps list — none of which is reused anywhere. The Agent transcript's folded line is the same object with a better name.

Decision (2026-09-02, after building A once): none of the three as written. The first build of A rendered the three create steps through ToolLine and nothing else — no rows reached agent_messages, and the conversation ended the moment the space opened. It was B wearing A's label.

What shipped is a fourth shape, the doorway. /spaces/new keeps the question, the openers, and the composer, and shows no transcript — there is nothing yet to show. On submit it awaits three local writes (the space, the words as its note, and a user turn in the transcript) and then hands the user to that space's Agent. The naming and the phrases run on past the screen and write their reply into the same transcript.

C stays rejected for a reason this mock did not name: AGENT_MAX_STEPS is 8 and the loop runs one tool call at a time, so seeding eight phrases through change_phrase is eight sequential round trips. describeSpace and seedPhrases also run in parallel today, and an agent loop cannot. The model still does not create.

The §5 frames below are therefore superseded: there is no progress list, no Open the space anyway, no Open Sister, and no auto-open decision. The argument for waiting was always about landing on Talk, whose suggestion stripe would fill under a reaching hand; Agent sets suggestions={false}, so it dissolves.

Three ways to do it

OptionWhat it meansVerdict
A · Seeded conversation
Keep the deterministic writes, render them as agent turns		 /spaces/new renders the Agent screen with no space yet. Pressing Create space still runs the same code path it does today — make the space, save the words, then describeSpace and seedPhrases in parallel under the 20s timeout — but each write reports as an applied tool line instead of a Steps row. When the run lands, the space is real, the conversation continues in it, and the user can say “add a phrase for mornings” without leaving. Recommended
B · Shared shell only Keep NewSpaceScreen's state machine and swap the Steps list for the transcript components. Cheapest change; the two screens still diverge in behaviour, and the user still cannot talk to the thing that just made their space. Fallback
C · Model-driven creation Give the agent a create_space tool and let the loop decide when to call it. Reads well; loses every guarantee the current flow has. A model that hangs or answers badly leaves the user with no space and their paragraph gone. No
Why not C. The current create flow has three safety properties worth more than the elegance: the space and the user's words reach local storage before any model runs; a model that stalls is abandoned at 20s and becomes a note beside its line, not an error; and a failed run patches the space it already made rather than making a second one. Option A keeps all three — the model never decides whether to create, only what to call it and what to write. The transcript is the presentation layer; it is not given the steering wheel.

6 · Decisions to make before code

#QuestionRecommendation
D1Does the agent's reply keep its grey bubble, or become prose on the surface?Prose. The agent is the app answering, not a second speaker. Long answers read badly in a balloon, and it halves the visual noise of a turn.
D2Do consecutive tool calls fold into one line, or stay one line each?Fold. “Read this space and 2 more”, expanding to the list. A turn with four reads is one row, not four. A write never folds into a group — it always gets its own line.
D3Is the tool detail shown as prose or as raw arguments and results?Prose keys, raw tail. A labelled key/value list at the top, and the raw tool result in a monospace block underneath, bounded and scrollable. Neither audience is left out.
D4New space: A, B, or C from §5?A. Every safety property kept, ~300 lines removed, and the create failure finally has a reader.
D5Do agent bubbles move from text-sm to text-base?Yes. DESIGN.md assigns text-base to the message-bubble role, and Talk already follows it. The Agent screen shipping at text-sm is drift, not a decision.
D6Should a folded line remember that it was opened?No. Fold state is per-row and resets on mount. A remembered fold means a returning user meets a screen full of open detail they last opened weeks ago.
Accessibility held throughout. Every fold, chip and button is ≥44px. The fold is a <summary>, so it is a real control with real keyboard behaviour and it announces its expanded state without help. Outcome is carried by mark and word, never by colour alone. The aria-live region still wraps the stream, and folded detail is inside it — so a screen reader hears “Read this space, collapsed”, not three paragraphs of tool output it did not ask for.
