Phrase codes, sentence starters & per-space corpus

One thesis — fewer keystrokes to full expression — served by extending what already exists. Saved phrases gain an optional code (ty → thank you). AI seeding also produces 3–5-word sentence starters and a per-space corpus that primes the on-device autocomplete. Phrases, starters, and code expansions all render through the one existing stripe component (word tiles + take key), differentiated only by gutter icon, tile tint, and end key.

Design: no new tables, no new UI components

  • Data — SavedPhrase gains code?: string and kind: 'phrase' | 'starter'. AI seeding assigns every generated phrase a code too (deterministic, client-side — not the LLM), so codes work from day one; AI codes are replaced with their rows on regen. A user-set code pins the row (user code ⇒ pinned), and pinning a phrase makes its code durable. No new collection.
  • One component — the existing suggestion stripe (word-tile rows with partial take: tap word i, take the sentence up to it). Phrases, starters, and code matches are just three row kinds of it — same tiles, same take mechanics, differentiated by icon + color (legend below). No second stripe, no pill variants, no "Say / Start with" sections.
  • Expansion — a ranking rule, not a feature: when the word at the caret matches a code, that phrase's row surfaces at the top, tinted, with its code in the gutter. Taking it consumes the typed code. Local lookup — instant, never waits on the LLM debounce.
  • Management — the existing Phrases tab gains an optional code field. Frequency-mined proposals appear there as suggested rows with a prefilled code.
  • Corpus — invisible; seeds the on-device n-gram engine per space at the existing seed/regen moments.
The user learns exactly one thing: short codes bring your phrases to the front. Everything else looks and works like the stripe they already use.
One component

Tapping any tile still takes the words up to it; tapping a starter's … takes the whole prefix and hands off to autocomplete.

Phrase

Complete thought. White tiles, ↵ key takes all of it. Filled pin = pinned by the user; muted pin = AI-suggested, tap the pin to keep it. Exactly today's stripe.

Starter

3–5-word opening. Dashed, indigo-tinted tiles; ends in … instead of ↵ because it isn't speakable as-is. Taking it fills the composer and completion continues from the prefix.

ty Code match

Surfaces while typing when the caret word equals a phrase's code. Filled code chip in the gutter, tinted tiles, solid ↵. Taking it swaps the typed code for the phrase.

Color discipline: all three stay inside the single indigo accent — differentiation is fill level (white → dashed tint → solid tint) plus the gutter icon, never a second hue. Semantic colors (amber/emerald) stay reserved for callouts.

Expansion

Typing a code: its row surfaces on top

The user types ty. The stripe's ranking sees the caret word matches a code and pins that phrase's row to the top — code chip in the gutter, tinted tiles, solid ↵. One tap on ↵ (or the last word) swaps the typed ty for "thank you". Partial take still works: tapping "thank" takes just that word. Rows behind it are the normal completion stripe.

Management

Phrases tab, plus one optional field

The existing right-panel Phrases tab is the whole management surface. Rows can carry a code badge; starters show the dashed variant of the same badge treatment. The add form gains an optional code input with a conflict check — no dictionary words, no duplicates. Frequency-mined proposals appear in the Suggested group with a prefilled code and the evidence; Keep pins phrase + code in one tap.

Frequency mining (all local, no LLM): over the last ~300 user messages — count exact repeats and maximal 3–8-word n-grams; score = count × keystrokes saved; threshold count ≥ 5 and ≥ 3 words; decay by age. Candidates matching an existing phrase — pinned or AI-seeded (those already carry codes) — are excluded, so mining only proposes what seeding hasn't covered. Codes come from the same deterministic generator seeding uses (content-word initials, mutate on dictionary/duplicate collision — checked against the autocomplete trie already in memory). Runs on app open when ≥ 20 new messages since last scan; persists only the dismissed-set and last-scan count. Dismissed proposals never return.

Corpus seed

Per-space autocomplete corpus — invisible, generated at seed time

No new UI. When a space's context is first generated (existing seed moment, after the first message), the same pipeline additionally generates ~100 short sentences a person would plausibly say in this space, and feeds them into the on-device n-gram engine scoped to the space. The engine then predicts space-appropriate words from message one — "physio" in the care-team space, "grandkids" in the family space — instead of relying only on the generic base corpus.

1

First message sent

Existing trigger: useSyncSpacePhrases decides seed. Space context + title are generated.

2

One structured call

Generator returns { phrases, starters, corpus[] } — ~100 sentences, 6–8 phrases, 4–6 starters — from space context + first message.

3

Feed the engine

Corpus sentences are observe()d into the autocomplete LM with a low weight, tagged with the space id, and persisted with a seed digest.

4

Real usage takes over

User messages keep the higher weight they have today. On phrase regeneration (staleness ≥ 6 msgs) the corpus can refresh too; a digest check skips no-op regens.

Weighting is the crux: seeded sentences must prime predictions without drowning the user's real voice. Proposal: count each seeded sentence as a single observation, let user messages accumulate naturally on top, and cap the seed layer so it can never outweigh ~20 real messages. The generic corpus.txt base layer stays untouched underneath both.

What else this unlocks (later, not now)

  • Speak-on-take for urgent codes — a flag on a phrase (hlp) so taking its code match speaks immediately: two keys from need to voice.
  • Fuzzy code match — the QWERTY-fuzzy trie already in the autocomplete package could tolerate one-key-off code typos (tu still surfaces ty's phrase) for tremor input.
  • Template slots — in5 → "I'll be ready in 5 minutes" with the number editable on take.
  • Import/export — phrases + codes as a small JSON file, shareable between users/caregivers.
  • Starter personalization — rank starters by actual pick-rate, not just generation order.

Open unknowns (need decisions)

  1. Enter/Speak auto-take — should speaking with a bare trailing code take the match first? Recommended: off for v1, revisit with usage.
  2. Cross-space code lookup — codes from other spaces match here (recommended), or strictly per-space?
  3. Starter row budget — with one shared stripe, how many rows total and what mix (e.g. 3 phrases + 2 starters when empty)? The stripe already caps rows; the mix ratio is the new knob.
  4. Notes mode — does code ranking apply in the Notes composer too? Recommended: yes, same stripe; verify against the tiptap surface.
  5. Corpus size & cost — is 100 sentences enough to shift a 5-gram model? Needs a quick offline experiment. Also: can WebLLM (privacy mode) produce 100 usable sentences, or does corpus seeding silently require a cloud provider?
  6. Seed-layer weighting — the cap proposal above is a guess; validate against the engine's actual scoring.
  7. Starter/code seeding — ship a small starter pack (ty, hru, iwb…) as pinned-with-code rows in DEFAULT_SPACE_SEED so the feature is discoverable day one? Recommended: yes, a handful.
